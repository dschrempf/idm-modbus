# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

    nix develop                        # toolchain: cabal, HLS, ormolu, cabal-fmt
    cabal build
    cabal test                         # prints one line per check
    cabal run idm-dump -- HOST         # read the registers a reference machine answered for
    cabal run idm-dump -- HOST --all   # sweep the whole parameter list
    cabal run idm-dump -- HOST --json > captures/navigator-2.0-scan-SOFTWARE-YYYY-MM-DD-HHMM.json
    cabal run idm-dump -- HOST --watch 10 1066 1012 > captures/navigator-2.0-watch-SOFTWARE-YYYY-MM-DD-HHMM.jsonl
    cabal run idm-dump -- HOST --widths 1534 1074 > captures/navigator-2.0-widths-SOFTWARE-YYYY-MM-DD-HHMM.json
    tools/transcribe.py manual/812170-rev12.txt --scan SCAN [--webapi WEBAPI --widths WIDTHS]
    IDM_PIN=... tools/webprobe.py HOST > captures/navigator-2.0-webapi-SOFTWARE-YYYY-MM-DD-HHMM.json
    IDM_PIN=... cabal run idm-web -- HOST --status      # user level, clock, notices
    IDM_PIN=... cabal run idm-web -- HOST --show 4768   # a setting, read for a person
    IDM_PIN=... cabal run idm-web -- HOST --watch 10 4768 5888 > captures/navigator-2.0-webwatch-SOFTWARE-YYYY-MM-DD-HHMM.jsonl
    IDM_PIN=... cabal run idm-web -- HOST --enter-fachmann   # and --leave-fachmann
    cabal run idm-write -- HOST 74 3.0               # a target; --eeprom where it costs a cycle
    ormolu -i $(git ls-files '*.hs')   # formatting
    cabal-fmt -i idm-modbus.cabal

The test suite is a list of `(name, Bool)` pairs in `test/Main.hs`; there is no
per-test selection, and a new invariant is a new entry in `checks`. It needs no
heat pump: everything is decoded from literal byte strings.

Reaching a real machine needs Modbus TCP switched on in the controller (service
level, "Gebäudeleittechnik", "Modbus TCP" to "Ein"; the service code is the day
and month of the current date). Port 502, unit id 1.

## Architecture

The register table is data, not code, and it flows one way:

    manual/812170-rev12.pdf → pdftotext -layout → tools/transcribe.py
      → data/navigator-2.0-{registers,enums}.tsv → splice → IDM.Navigator.Table
      → src/IDM/Navigator/Target.hs (with data/navigator-2.0-targets.tsv)

`tools/transcribe.py` is the only thing that may write those two TSVs and
`IDM.Navigator.Target` — editing them by hand makes the next revision of the
manual impossible to apply cleanly.

The targets, the registers a write may go to, are a hand-written list,
`data/navigator-2.0-targets.tsv`: an address and an English constructor name
each. Only listed registers can be written, and listing one goes with trying
on the machine that a write to it takes effect. The script refuses an address
the table lacks or nothing may write, a write-only register whose write costs
an EEPROM cycle, and a member of a heating circuit or zone module family,
which would need the circuit or module as an argument and is not generated
yet. The cost of a write, `'Free` or `'EepromCycle`, is derived from the row;
`targetCost` takes it from the table through `$(costAt …)`, so the build fails
where a constructor's type and the table disagree, and `$$(registerOf …)`
repeats the script's refusals.
Given a scan, `captures/navigator-2.0-scan-*.json`, it fills the `observed`
column from what one machine answered; without one it carries the column over
from the table it replaces, so the table can be regenerated by someone who
does not have the scan. The rows of the `source` `gltmon` come the same way:
the controller's web page `N2_GLTMON` lists addresses the manual does not,
and given a webapi capture holding that page and a widths capture of those
addresses, the script adds them, with the width measured and everything the
page does not state left unstated; without the two it carries them over. Their
parameter identifier is the one input written by hand,
`data/navigator-2.0-gltmon-parameters.tsv`: the page names no identifier and
the settings tree no address, so only moving a setting and watching which
register follows can join them. The script reads that file in either case
and, given the webapi capture, refuses a join the capture contradicts. The scan holds no transcribed data of its own —
`idm-dump --json` writes it, and it records only address, status, exception
code, raw bytes and the uninterpreted number, so a correction to the table
cannot leave it saying something else. A defect in a register name, unit or
range is therefore a defect in the transcription script, not in the Haskell
parser.

The table describes one software of the controller, the one its captures
were read on, and `data/navigator-2.0-software.tsv` states it by hand:
series, major, minor and patch, `unknown` where a part was never read. The
script reads it and refuses a capture recorded on another software. A write
goes ahead only on it, a read on any. Every session reads the software when
it opens, and again when a connection is made anew: over Modbus major, minor
and patch at 522, 524 and 526, over the web series, major and minor from
`N2_SYSTEM_INFO`, setting 4754. Each channel compares what it reads. Every
capture records the software of the session it was read on, and its name
carries the software, as `captures/README.md` says.

`data/navigator-2.0-web-*.tsv` is a different kind of file and is written by
hand: what the controller's own web pages showed, at the minute they were read.
It carries no addresses, so the mapping it tests is stated only in the register
table; the join is on the sensor designator a register name already holds.

`captures/navigator-2.0-webapi-*.json` is the third kind: what the controller's
web interface answered, captured rather than transcribed. `tools/webprobe.py`
writes it over the websocket the web interface itself uses, sending only the
three read commands the controller's own JavaScript names, `overview`, `detail`
and `traverse` — the protocol's `save` and `execute` must stay out of that
script, and so must the two reads that open the relay test and ask for user
level 4. It is the stronger witness of the two web sources, because the
settings it walks name their value with the manufacturer's own parameter
identifier, the `FW030` and `BV002` of the parameter list, so the join to the
register table is on the identifier the table already carries. It is also the
only source that carries time: the graph it captures says when the machine ran,
which is what a rise in a counter has to be attributed to. The capture is
verbatim but for the code that opens the controller and the strings that name
the machine, which are replaced by a visible marker. What the capture contains
depends on the user level the controller is left at; the script never raises
it. At Fachmann level the settings tree also holds controls — the relay test, a
reboot, resets. The web interface acts only on a `save` or `execute`, but of
the controls only `N2_PING` has been asked its `detail`, so the walk asks
`detail` only of the item types in `VALUE_ITEMS` and never opens the menus in
`CLOSED_MENUS`; a new item type stays unasked until someone has seen what its
`detail` does. `idm-web --show` asks whatever id it is given.

Captures of either kind live in `captures/`, which git ignores because the
repository is public; `captures/README.md` names the files. A document in
`doc/` cites a capture by its path there.

`manual/` holds the manufacturer's PDFs and is ignored by git; copy them in
from the house documents to re-run the transcription. The list is printed
inconsistently — the same column appears in a different order on different
pages — so cells are read by the column they are printed in, taken from the
page heading, not by the order they appear in.

The modules stack, each refusing to know the next one's business:

- `IDM.Modbus.TCP` — framing and sockets for the two read function codes and
  the two write ones, 6 and 16. Returns raw bytes in wire order and a
  `Failure` for anything else. A request that leaves the stream out of step —
  no answer in time, an answer to another request — ends the connection, and
  later requests fail unsent.
- `IDM.Navigator.Register` — the manual's vocabulary as types, plus `decode`
  and its inverse `encode`. Every distinction the manual draws in prose or a
  footnote is a constructor, so a caller cannot silently ignore it.
- `IDM.Navigator.Table` — parses the TSVs at compile time, so a row that does
  not parse fails the build; exposes `navigator20`, `readable`, `present`,
  `enumLabel`, and `navigator20Software`, the software the table describes.
- `IDM.Navigator.Software` — a version as the table states it and as each
  channel reads it, and whether the two agree.
- `IDM.Navigator.Client` — sessions, pacing, and pairing a read with its enum
  label. A `Session` reads the software when it opens; `writable` gives the
  `Writable` that `write` needs only on the software the table describes.
- `IDM.Navigator.Target` — generated: `Target (c :: Cost)`, a constructor per
  target, and `targetRegister`, total.
- `IDM.Navigator.Write` — `write`, whose `Outcome c` carries the cost. An
  EEPROM write reads first and sends nothing when the value is held already;
  a volatile one always sends. Both read back. The decision is `writeWith`
  in `IDM.Navigator.Write.Core`, over any register and any monad, so the
  test suite runs it against a fake controller in `State`. It lives with
  `IDM.Modbus.TCP` and `IDM.Navigator.Register` in `core/`, the private
  sublibrary `core`, which the library re-exports but for that module: a
  consumer reaches a register only through a target.

The web backend has a stack of its own beside it, joined to the first only by
`Host` and by the parameter identifier:

- `IDM.Navigator.Web` — the protocol's vocabulary: `Query`, which has a
  constructor for each read and none for `save` or `execute`, and parsers that
  hand back an answer they do not recognize rather than read it as empty.
- `IDM.Navigator.Web.Connection` — the websocket; sends any JSON, so the
  package does not expose it.
- `IDM.Navigator.Web.Session` — sends a `Query` and nothing else. Reads the
  software when it opens, and gives the `Writable` the two writes of the
  level need.
- `IDM.Navigator.Web.Level` — the two writes: entering the Fachmann level
  (`setting`/`save` of item 12503, a code spelled from the controller's clock,
  as a number, from Kunde only) and leaving it (acknowledging the `N2_USERLEVELACTIVE` notice).
  Both work on the machine, and the display switches with them. The level is
  the controller's, not the connection's: it holds until it is left or for
  sixty minutes from the entry, whichever comes first, however often it is
  read meanwhile. The frost protection wizard's code
  page is not a way in: it answers "wizard is not available!" unless a wizard
  runs.

Writing some registers wears out an EEPROM (a register's `Persistence`), so
the cost is in the type of every target and every outcome rather than in an
extra argument, and `idm-write` refuses an EEPROM target without `--eeprom`.
A confirmed write says the register stored the value, not that the controller
acts on it; checking that is the consumer's concern.

The package is an interface to the controller and stays one: it reads, it
sets the user level, and it writes. Deciding what the heat pump should
do — from a PV surplus, a meter, a tariff, the household's appliances — belongs
to its consumers, and no such strategy goes in here, not even as an example. A
write of the surplus register 74 is interface; computing the surplus is not.

## Things the wire does that surprise people

- A 32-bit float arrives **low word first**, against the usual Modbus habit.
- An unfitted sensor answers with a sentinel (`-1.0` for a `FLOAT`,
  `-1` for a `UCHAR`, `65535` for a `WORD`), not an
  exception; `decode` returns `NoValue` so a -1 never enters a temperature
  series. A `FLOAT` whose documented range does not rule -1 out — most
  document none — decodes it to `NoValueOr`, since -1 °C is a temperature;
  the caller decides. A `WORD` is two's complement where the parameter list documents a
  negative minimum for it, and there 65535 is a value rather than a sentinel:
  the pump control signals at 1104 to 1109 read it as "not being driven".
- A `UCHAR` arrives as a whole register, `ffff` and not `00ff`, and the
  controller reads it as a signed word: it prints the `fffe` of 1714 and 1715
  as -2.
- The Navigator stalls when polled hard, hence `pollIntervalMicroseconds`.

## Conventions

- Documents go straight into `doc/`, not into the AI directory's `doc/`. They
  are part of the project's argument for why the table can be trusted, so they
  are written and reviewed like source. Plans, TODOs and scratch notes still go
  to the AI directory.
- Haddock header on every module: name, description, copyright, license.
- German register names and the manufacturer's identifiers (`FLOAT`, `FW030`,
  `B32`) are quoted verbatim; prose is US English.
