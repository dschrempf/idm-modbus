# Changelog

## Unreleased

### Added

- Modbus TCP framing for the two read function codes.
- The Navigator 2.0 parameter list of document 812170 revision 10, transcribed
  to `data/navigator-10-registers.tsv`, embedded at compile time.
- Decoding that distinguishes a measurement from the sentinel an unfitted
  sensor returns, and that reads a `WORD` as signed where the parameter list
  documents a negative minimum for it.
- `idm-dump`, which reads every register and prints it.
- The research behind all of this, in `doc/`.
- The 166 registers the parameter list marks `RW/RO`, an access right chapter
  4.1 never defines and the transcription used to skip: the energy management
  block at 74 to 86 — PV surplus, house consumption, battery charge level —
  and every zone module room temperature and humidity. The table now has 663
  registers rather than 497. `Access` gained `Supplied` for the marking, read
  as "the building management system may supply this value, and may read it
  back". This settles address 86, which `doc/research.md`, now `doc/sources.md`, had listed as
  documented nowhere: it is `Batteriefüllstand`.
- `idm-dump HOST --watch SECONDS ADDRESS...`, which reads a few registers
  round after round and writes a line per read, the capture format plus the
  local time the read was asked, so a charge can be followed at a finer step
  than the controller's own graph keeps. A stalled or lost connection is opened
  again at the next round, as a new session, and the reads it cost are
  recorded as errors.
- `Drive`, what a pump's control signal says: `NotDriven`, or `Driven` so many
  per cent. The controller's scale runs from -1, and `Driven 0` — a pump at its
  minimum speed — is not a pump at rest.
- `IDM.Navigator.Web` and `idm-web`: a client for the controller's web
  backend, the websocket on port 61220, beside the Modbus stack. A session
  sends only the reads, `overview`, `detail` and `traverse`, and its request
  type has no constructor for anything else. Settings arrive with the
  manufacturer's parameter identifier, and the info pages parse to rows of
  designator, label, value and unit. `idm-web --watch` follows settings round
  after round, to `captures/navigator-10-webwatch-*.jsonl`.
- `IDM.Navigator.Web.Level`: entering and leaving the Fachmann level, the
  only writes the library knows, sent as the settings and notices pages of
  the web interface send them. The code is sent from Kunde only, and never
  so close to the hour that it could arrive in the next one; the result says
  whether anything was sent.
- A second verification, `doc/verification/2026-09-20-display.md`, checking the
  table against the controller's own display rather than against the machine
  alone, with the readings in `doc/verification/2026-09-20-display.tsv` and the
  two captures taken beside them.
- Nineteen registers the parameter list does not print, taken from the
  controller's own list of what it serves, the web page `N2_GLTMON`: the
  minimum and maximum flow temperature of circuits A, C and D, the heat sink's
  return, flow and flow rate, the total electrical energy, and power limits.
  The page states a name, a unit and an access right, so `Register` gained
  `registerSource`, `Datatype` gained `OneRegister` for a width with no
  encoding stated, and `Persistence` gained `UnknownPersistence`. The table has
  682 registers. `idm-dump HOST --widths ADDRESS...` measures how many
  registers wide the value at an address is, to
  `captures/navigator-10-widths-*.json`; see
  `doc/verification/2026-10-14-gltmon.md`.
- The minimum and maximum flow temperature of circuits A, C and D, 1520 to
  1540, carry their parameter identifiers, `HSA05` to `HSD04`, joined by
  moving one circuit's setting at a time and watching which register followed
  (`doc/verification/2026-10-15-flow-temperature.md`). The join is written by
  hand in `data/navigator-10-gltmon-parameters.tsv`, which
  `tools/transcribe.py` reads and checks against a webapi capture. The heat
  sink's 1068 to 1072 are B124, B125 and B2, read beside the display, and 4126
  is computed from them (`doc/verification/2026-10-15-heat-sink.md`).
- Writing. `IDM.Modbus.TCP` sends function codes 6 and 16 and checks the
  device's echo, a mismatch being `UnexpectedEcho`; a write is of `One`
  register or `Two`, as wide as a datatype goes, and a read's `Quantity` is
  made by `quantity`, 1 to 125, so a request Modbus forbids cannot be built.
  `encode` is the inverse of `asWritten` and refuses a value the register
  cannot hold. A write goes to a
  `Target (c :: Cost)`, generated by `tools/transcribe.py` into
  `IDM.Navigator.Target` from the hand-written
  `data/navigator-10-targets.tsv`, so the cost, `'Free` or `'EepromCycle`,
  is in the type; `write` in `IDM.Navigator.Write` returns an `Outcome c`. An
  EEPROM write reads first and sends nothing when the value is held already,
  and every write is read back. The first target is the PV surplus at 74.
  `idm-write HOST ADDRESS VALUE` writes it, and writes an EEPROM target only
  with `--eeprom`.
- A guard against an unannounced update of the controller's software. The
  software the table describes is stated by hand in
  `data/navigator-10-software.tsv`, now 20.24-2608, patch 0,
  and `tools/transcribe.py` refuses a capture read on another. A session reads
  the software when it opens: `IDM.Navigator.Client.open` over Modbus, major,
  minor and patch at 522, 524 and 526; `IDM.Navigator.Web.Session.open` over
  the web, series, major and minor from `N2_SYSTEM_INFO`. `write`,
  `enterFachmann` and `leaveFachmann` take a `Writable`, which `writable`
  gives only for a session on the table's software, and an `IDM.Navigator.Software.Mismatch`
  otherwise: not read, another software, or one the table cannot confirm.
  `idm-write` and `idm-web --enter-fachmann`/`--leave-fachmann` refuse with
  both versions; a read goes ahead and warns with both.
- `IDM.Modbus.TCP`, which the library re-exports, no longer exports
  `connect`, `withConnection`, `disconnect`, `Write`, `writeRegisters` and
  `parseWriteResponse`; they moved to `IDM.Modbus.TCP.Internal`, private to
  the package. A consumer can no longer write an address past the targets
  and the guard, and its only `Connection` is a session's, whose software is
  read.
- Every capture records the software its session read: a scan, a widths
  and a webapi capture as `software` beside `entries`, each line of a watch
  as a field `software`, the output of `idm-web` as a first line. A capture's
  name carries the software, and the captures made before were renamed by
  the controller's log.
- A second target, `PvTarget`, 88 `PV-Zielwert (Smartfox und Solar-Log)`,
  the candidate for the target the controller's PV loop holds 74 at. It
  stores what is written, but neither -1.0 nor +1.0 moved a PV run
  (`doc/verification/2026-11-07-pv-target.md`,
  `doc/verification/2026-11-07-pv-target-ignored.md`).
- A third target, `HeatPumpPowerLimit`, 4108
  `Leistungsbegrenzung Wärmepumpe`. A limit from 1.0 to 1.5 kW caps a PV
  run after its start program, also when lowered under the run, and one
  below 1.0 kW ends it; one capped at 1.0 kW ended after 30 minutes, short
  of `PV006`, for a reason not yet known
  (`doc/verification/2026-11-08-power-limit-cap.md`,
  `doc/verification/2026-11-09-power-limit-floor.md`,
  `doc/verification/2026-11-09-power-limit-held-at-1-0.md`,
  `doc/verification/2026-11-07-power-limit.md`), and a restart returns it to
  its default, -1, so its cost `'Free` holds
  (`doc/verification/2026-11-07-restart.md`).
- `tools/drivepv.py`, which writes a schedule fixed before a run to 74, 88
  and 4108 through `idm-write`, phase by phase, beside a running
  `idm-dump --watch`, and writes final values to all three when it ends, so
  no value it was writing stays behind. `tools/runtable.py` lines up a run's watch,
  webwatch and write log by time, with the mean of 74 the controller weighs.
- `Code`, the `Value` of a register whose number is a code of an
  enumeration, as against a `Count`. `Register` gained `registerScale`, a
  `Scale`, `Magnitude` or `Enumeration`, which `tools/transcribe.py` derives
  from the labels into a `scale` column of the table: a labeled register is
  an enumeration, but for a `BOOL` and a percentage, whose labels mark points
  of its scale. `decode` gives an enumeration a `Code`, `encode` takes one
  there and refuses a `Count` as a `Mismatch`, and the reverse. `idm-write`
  reads its value as the register's scale says.
- `data/navigator-10-measured-enums.tsv`, the codes measured on the machine
  that the manual does not print, written by hand, each with the document
  holding its evidence. `tools/transcribe.py` adds them to the enumerations,
  widens the register's range to a code outside it, and refuses a code the
  manual labels already. It holds 1005's -1 "Aus" and 3 "Urlaub"
  (`doc/verification/2026-10-15-web-app.md`).
- The heat pump's request reason, from the web backend. `Query` gained
  `SystemOverview`, the `system` `overview`, and `operation` reads its
  `heatpump` to an `Operation`: the `OperationMode` and the bits of `info`,
  each a `Reason` by the key the web interface translates, `PV` among them,
  and `Unnamed` for a bit the mode does not name. `reasonBits` states the
  bits per mode, `reasonKey` the keys; `askOperation` asks for it.
  `idm-web --status` prints the mode and the reasons.
  `idm-web HOST --watch SECONDS --reason SETTING...` asks the
  `system` `overview` first in every round, a line of its own in the
  webwatch capture, with no setting needed; `tools/runtable.py` adds its
  `mode` and `info` columns.
- `IDM.Navigator.Rounds`, the loop of `idm-dump --watch` as a library. A
  part of a program names its `Need`, the registers it reads, and `rounds`
  reads the union of the needs once per `Period`, in one session, each
  register once in the order of first mention, and hands each need a
  `Round` of the reads it named. A read is an `Asked`, with its local and
  monotonic time, its session and its `Sample`, or none where no session
  was open. A lost connection ends the session, the rest of the round is not
  asked, and the next round opens a new one. The library prints nothing:
  each read, opening, failed opening and loss is a `RoundEvent`, handed to a
  callback as it happens. `readRound` reads one round over any
  `RoundRequests`, so the test suite runs it against a fake controller.
  `IDM.Navigator.Client.sampleOf` makes a `Sample` from what a read returned.
- `IDM.Navigator.Capture`, the line of a watch capture, `watchLine`, over an
  `Asked`, and the fields the scan and widths captures share with it.
  `idm-dump --watch` prints its lines from the `RoundEvent`s of `rounds`,
  each as its read is made, unchanged but that an address given twice is
  read once a round.
- `IDM.Navigator.Table.readableAt`: the register at an address where a read
  may ask it, or `Unreadable`, `Unlisted` or `WriteOnlyRegister`, why not.
- `tools/runtable.py` reads the drive file of `idm-drive` as its WATCH: the
  reads as a watch's, and the writes of 74 for the mean from the file's
  `write` events the controller acknowledged, so it needs no `--writes`,
  which stays for the write logs of `tools/drivepv.py` and is refused beside
  a drive file. A drive file's `export` events add the columns `export`, the
  PV less 4122, and `written`, the value the bounds left of it, in the row
  of the round whose 4122 they came from. A webwatch with level lines adds a
  `level` column, the user level each round was read at, and in a round not
  at Fachmann the speed and power of 6245, which then has no answer, are
  `-` rather than the last ones read. `tools/test_runtable.py` tests it on
  hand-written captures in `tools/fixtures/`, and the dev shell has
  `python3`.
- `idm-web HOST --watch SECONDS [--reason] --fachmann SETTING...` holds the
  Fachmann level for the watch. It reads the level first in every round,
  enters it at the beginning, renews it 55 minutes from each entry by
  leaving it and entering 30 s later, enters again where it fell back, and
  leaves it on every exit, SIGINT and SIGTERM included. After three entries
  in a row that did not take, 30 s apart, it reads on at Kunde. It exits
  having sent nothing on other software, at a level neither Kunde nor
  Fachmann, or at Fachmann without the notice that closes it. Each change of
  level is a line of the webwatch with `captured`, `software`, `level`,
  `userLevel` and `error`, and with no `request`.
- `IDM.Navigator.Drive`, the loop of a driver. `drive` reads, round after
  round, what its needs and its step name, hands the step its reads, and
  writes the `Command`s it answers with, each to a `Target 'Free`, on the
  round's session and only where `writable` gives a `Writable`; a command it
  cannot send is `Skipped`, with no session or on other software. On every
  exit, the step's own end or an exception, a signal's included, it writes
  the final values in their order, under the ordinary mask, and opens a
  session for them where none is, up to three times, 10 s apart. Nothing
  thrown once the finals began stops them: a write or an opening that
  throws counts as the session lost, and a callback that throws is thrown
  again after them. It ends with `Finish r`, the step's reason or the
  exception. The library prints nothing and installs no signal handler:
  each read, opening, loss, write, skip and the start of the finals is a
  `DriveEvent`, handed to a callback.
  `driveWith` drives over any `DriveRequests`, so the test suite runs it
  against a fake controller. `IDM.Navigator.Rounds` gains `NeedOn`, a need
  on any session, `restrict` and `handOver`, and `IDM.Navigator.Capture`
  gains `endingText`, from `idm-dump`.
- `idm-drive HOST SCHEDULE` runs a schedule file of `schedules/` on the
  controller: one session, the schedule's watch and 1100 and 4122 read
  every round, and its writes of 74, 88 and 4108, with the finals to 88,
  4108 and 74 on every exit, SIGINT and SIGTERM included. A round without a
  session on the software the table describes is not stepped, so a phase
  begins in the first round that can write; what such a round leaves in the
  stream, and why a drive on other software runs until a signal, is in
  `IDM.Navigator.Schedule.Log`. It prints one
  JSONL stream, the reads as `idm-dump --watch` prints them and a line per
  event, `begin` with the pid and the schedule's text first and `end` with
  why last. `idm-drive --check SCHEDULE` reads the schedule, prints its
  phases and connects to nothing.

### Changed

- The documentation in `doc/` is by topic: `sources.md`, `modbus.md`,
  `registers.md`, `web-backend.md`, `heat-pump.md`, `pv-control.md` and
  `software-versions.md`, listed in `doc/README.md`. `doc/research.md` is
  split among them. The measurements moved to `doc/verification/`, without
  the `verification-` prefix.

- The controller is a Navigator 10, not a Navigator 2.0: its firmware and web
  interface name it, and iDM's 2025 catalog lists the AERO ALM with it. It
  serves the register map of 812170, the Navigator 2.0's manual, which the
  table still rests on (`doc/sources.md`). The data files are
  `data/navigator-10-*.tsv`, captures are named `navigator-10-*`, and
  `IDM.Navigator.Table` exports `navigator10` and `navigator10Software`
  rather than `navigator20` and `navigator20Software`.
- The table is transcribed from revision 12 of 812170, for software 20.23-515,
  rather than revision 10: 694 addresses rather than 663. New are the Smart
  Grid status at 90, which moves there from 1006, the groundwater
  temperatures at 1086 and 1088, faults at 1680 to 1683, and two boosters at
  4001 to 4052. 1006 is the `Variabler Eingang` now. 88, 1068, 1070, 1074,
  4108 and 4124, rows of `N2_GLTMON` so far, are the manual's, with
  persistence, range and default. 1072 stays the page's `FLOAT`, since
  revision 12 prints a `UCHAR` where two registers answer. The bivalence
  points run from -40 rather than -90, the pump signals from 0 with a default
  of -1, and the cascade block has no parameter identifiers.
- The table describes software 20.24-2608 and has 722 registers, 30 of them
  from `N2_GLTMON`. New from the page: the myiDM identifier at 500, the heat
  source and heat pump type at 506 and 508, the software at 520 to 526, an
  interlock at 1174, five alarm codes at 1950 to 1958, locks at 4110, 4113
  and 4114, and 4126 and 4128, which revision 12 drops and the controller
  serves. 4112 is gone: revision 12 prints the `FLOAT`
  `Leistungsbegrenzung Kaskade`, 4113 now answers on its own, and the page
  names nothing there. Every address the table holds was read on the
  machine.
- The table is transcribed from 812663 revision 0, "Modbus TCP Navigator
  10", the Navigator 10's own manual, rather than from 812170 revision 12,
  the Navigator 2.0's. It has 612 registers rather than 722: the 110 of the
  zone modules' rooms 7 to 9, which 812663 does not print, are gone, with
  their enumerations. Nothing else changes. `tools/transcribe.py` crops the
  page to the type area, so 812663's thumb index does not enter the rows.
- `tools/transcribe.py` takes a value one register wide where the address
  after it answers on its own, drops a manual row the width measured
  contradicts even where the page names nothing in its place, and drops a
  manual row two registers wide whose second register is a row of the page,
  so the rows carried over drop it again. A page value `true` or `false`
  counts as a value, and a name the page prints without a unit keeps its
  parentheses: `Softwaretype (bitcodiert)`.
- A `WORD` is two's complement also where the parameter list documents a
  negative default for a read-only register: revision 12 moves the pump
  signals' -1 there. The battery level at 86, which the building management
  system supplies, keeps its -1 as the sentinel. 1074 reads as a `Drive`.
- `tools/transcribe.py` takes the PDF rather than its text, and reads the
  type's height with `pdftotext -bbox`: a remark revision 12 prints directly
  below a name is set smaller, and nothing else tells them apart. Where the
  manual and `N2_GLTMON` name the same address, the manual's row stands unless
  the width measured contradicts its datatype; the rows carried over used to
  replace the manual's. A default printed nearer the unit's heading is read
  as the default, and an enumeration may have a negative code.
- `Unit` gained `EuroPerMegawattHour`, the electricity price's at 1048.
- `readOne`, `readMany` and `probe` take a `Session`, which holds its `Poll`,
  rather than a `Connection` and a `Poll`; `idm-dump` opens one per connection.
  A scan and a widths capture are an object rather than a list, and a webapi
  capture too; `tools/transcribe.py` reads both forms.
- The sign of a `WORD` follows the minimum the parameter list documents for it,
  not its unit. Registers documented from a negative minimum — the bivalence
  points from -90, the pump control signals from -1 — are two's complement, and
  65535 is a value they may hold rather than a sentinel. This replaces the
  special case for degrees Celsius instead of adding a second one, and a
  bivalence point set to -1 °C is no longer swallowed.
- `Reading`'s `NotFitted` is `NoValue`: the sentinel says that a register
  holds no value, not that hardware is missing, and the fitted B33 and B34
  answer it at 1050 and 1052. A `FLOAT` -1.0 is `NoValue` only where a
  documented range excludes -1; elsewhere it is the new `NoValueOr`, no value
  or -1, which an outdoor temperature averaged to hundredths reads every
  winter. `reading` takes a function for each. `idm-dump` prints `-- or -1.00`
  for one and counts them apart.
- `Unit` lost `Unitless`, which nothing built: a register whose source states
  no unit has `registerUnit` `Nothing`.
- The table is parsed when the library is compiled, and a row that does not
  parse fails the build. It used to be dropped, so a revision of the manual
  using a datatype the library does not know, such as `CHAR`, would have lost
  its rows without a word. A cell that is stated is read or refused: a
  default or bound that is not a number, or a range with one bound, fails too.
  `ParseError` is gone, and the types of a register derive `Lift`.
- `captures/navigator-10-scan-20.24-1574-2026-09-19-1503.json` is a fresh sweep of all
  663 addresses: 232 answered, 431 refused, every refusal `IllegalDataAddress`
  and every one of them in the zone module block or write-only. It reproduces
  the earlier sweep of the 497 addresses then known, sentinel for sentinel.
- The same file holds what the machine said and nothing else: address, status,
  the exception code behind a refusal, the bytes, and the number those bytes
  spell. It used to repeat the parameter list's own columns, transcribed a
  second time and wrong in 19 of them — the same defects as the table, plus a
  few of its own. `idm-dump --json` writes
  the format, so the capture is reproducible; `IDM.Navigator.Register.asWritten`
  reads bytes without applying the conventions the manual leaves out, which is
  what a capture must record if it is to be the evidence for them.
- `connect` and `withConnection` take a `Patience`, which bounds connecting
  and each read; `defaultPatience` is five seconds. A read that fails so that
  the stream is out of step or gone ends the connection: it closes the socket,
  and every later read fails without being sent. `Failure` says which, `Ended`
  or `Unsent`, and why, an `Ending`: no answer in time, an answer to another
  request, a malformed frame, the device closing the connection, or a socket
  error, which `readRegisters` no longer throws. `ConnectionClosed` is an
  `Ending` now. `parseResponse` reads a frame as the answer to its request.

### Removed

- `tools/drivepv.py`, whose place `idm-drive` took. The verifications that
  ran it name the last commit that has it. `tools/runtable.py --writes`
  stays, for the write logs of the runs before.

### Fixed

- `readRegisters` took whatever answer came next for the answer to its request.
  A caller that timed a read out and kept the connection read the late answer
  as the answer to its next request. It now checks the transaction id.
- A request that an exception interrupted, such as a drive's on SIGTERM, left
  the connection open with its answer still on the way, and the next request,
  a final value among them, failed on that answer. The interruption now ends
  the connection, as `Abandoned`, and later requests fail unsent.
- `idm-dump HOST` and `idm-dump HOST --json` waited for good on a Navigator
  that stalled; only `--watch` timed its reads out.
- Addresses 1104 to 1109 reported a fitted pump as absent. They are pump
  control signals documented from -1, so their 65535 means "not being driven",
  which the controller's display confirms for the charge pump M73 while showing
  it running. A pump nothing calls for and a pump never installed answer alike,
  and the library no longer pretends to tell them apart.
- `enumLabel` reached only the register the manual prints an enumeration
  beside, so the operating mode of heating circuits B to G, their active mode,
  and compressors 2 to 4 had no labels. `tools/transcribe.py` now shares an
  enumeration across the registers that differ only in the letter or digit
  ending their name and agree in everything else, and refuses to share where
  two of them carry enumerations of their own. Sixteen addresses became 45.
- Zone modules 2 to 10 had no labels: the manual prints them beside zone module
  1, and a zone module's number is inside the name, not at its end. The family
  rule now reads that number as an index too, and 45 labeled addresses became 207.
- `tools/transcribe.py` read the parameter list by the order of its cells,
  which the list does not keep. It now reads each cell by the column it is
  printed in. Sixty-six names were wrong — 59 cut short of their sensor
  designator, `Außentemperatur (B32)` down to `Außentemperatur (B3`, because a
  footnote marker is printed the same way, and 13 broken across two lines, so
  that addresses 1206, 1208 and 1210 all read
  `Kaskade / Gemittelte Vorlauftemperatur`. Twelve cascade registers lost their range and carried a
  number where the controller's parameter identifier belongs; nine more lost
  their unit.
- Info rows kept HTML entities: `Taupunktwächter&nbsp;Heizkreis A`. A cell now
  reads a no-break space as a space, with or without the semicolon the
  controller sometimes leaves off, and decodes the escapes of markup; any other
  entity stays as it is.
- `redact` and `tools/webprobe.py` stripped the machine's identity by
  different rules, and both missed a MAC address in lowercase. Both now match
  the myIDM identifier and the MAC address in either case, in keys as well as
  values, after the JSON is decoded, and drop the session identifier at any
  depth.
- `N2_GLTMON` prints the myIDM identifier as the value of 500, as a number,
  where neither rule matched it. Both now redact the value cell of that row,
  and `tools/transcribe.py` takes the marker for a page value, so 500 stays a
  row of the table.
- With 500 in the table, `idm-dump` read the myIDM identifier and printed it,
  and wrote its bytes into scans, watches and widths captures. A read that
  takes in 500 or 501 now shows `<redacted>` for its bytes and its number.
  `IDM.Navigator.Table.myIdmAddress` states the address for both channels.
- A setting the user level does not reach was a `NoAnswer`, which ended the
  session after waiting out its patience. The controller refuses it under
  `setting`, for a detail as well, and names the setting only in the text.
  `replyTo`, formerly `answerIn`, reads that as `Inaccessible`, a request
  fails with `Refused`, and the session goes on. `idm-web --show` names the
  user level beside a refused setting and goes on with the next.
- 1005, the operating mode, read a machine switched off for no value: "Aus"
  arrives as `ffff`, the word of an unfitted sensor. Its range now reaches
  the measured -1, a `UCHAR` reads a negative word inside its range as a
  value, and 1005 reads `Code (-1)`, "Aus", and `Code 3`, "Urlaub".
- The help of `idm-web` and the documentation of `IDM.Navigator.Web.Level`
  said the Fachmann level holds for sixty minutes from the entry. That was
  20.24-1574; on 20.24-2608 the controller ended it after as few as eight
  minutes, and once not within 73.
- They say sixty minutes again: a watch on 20.24-2608 measured them on
  2026-11-09.
- `tools/runtable.py` stopped on a web watch that read a setting answering a
  number rather than a page, such as 10389 `PV011`: it parsed every answer as
  HTML. It now reads only the two settings it takes a column from.
